# 001 — Native clients on the system's git

**Status:** `IN PROGRESS` — macOS skeleton built: add a repository, its changes, a file's diff; Linux not started
**Started:** 2026-11-11

## Problem

GitHub Desktop is **1.1 GB** installed on the owner's Mac and slow to open.
The weight is structural, not a bug that will be fixed: it is an Electron
app, so it ships Chromium and Node, and it bundles its own build of git
(through `dugite`) rather than use the one on the machine. Every update
downloads all of it again.

The owner wants the same app, native and light, for macOS 26+ on Apple
silicon first and Linux later, open to anyone (owner, 2026-11-11). Three
choices shape everything after them: the UI toolkit, how we drive git, and
whether the two platforms share code.

## Options

### UI toolkit

- **A. The platform's own toolkit on each OS.** Chosen. SwiftUI, with AppKit
  where SwiftUI falls short (large text views, some table behaviour), on
  macOS; GTK4 and libadwaita from Rust on Linux, as Dhun's Linux app already
  does. Each app looks and behaves like its platform, starts in a fraction of
  a second, and costs only its own code on disk: the frameworks are already
  on the machine.
- **B. Tauri or another system-webview shell.** Rejected. Much smaller than
  Electron, but still an HTML UI in a browser engine, which is the thing we
  are leaving; WebKitGTK on Linux is heavy and lags behind.
- **C. One cross-platform native toolkit (Qt, Slint, iced).** Rejected. Qt
  looks foreign on the Mac and adds tens of megabytes of frameworks to
  bundle; Slint and iced are young, change their APIs, and lack mature
  accessibility and large-list support.
- **D. Flutter or React Native.** Rejected. A bundled engine, the same
  objection as B.

### How we drive git

- **A. Run the system's `git` and parse its machine-readable output.**
  Chosen. Everything the user configured just works, because it is the same
  git they use in a terminal: hooks, credential helpers, SSH agents, commit
  signing (GPG, SSH, `gpg.format`), LFS filters, `includeIf`, worktrees,
  sparse checkout, `fsmonitor`. Nothing to bundle, and the user's git gets
  security fixes without our release. The output formats we read
  (`status --porcelain=v2 -z`, `--format=` strings, unified diffs) are
  documented as stable for scripts. A process per call costs a few
  milliseconds, which is nothing against the I/O git does anyway.
- **B. libgit2 (or SwiftGit2 over it).** Rejected. A C library to build,
  bundle and update for two platforms. It does not run hooks, handles SSH
  through libssh2 rather than the user's `ssh` and agent config, leaves
  commit signing and LFS to us, and lags git on newer features. Every one of
  those gaps is a "works in the terminal, not in the app" bug.
- **C. gitoxide.** Rejected. Rust only, so no help on the Mac, and push and
  several write paths are still incomplete.
- **D. Bundle a git build, as GitHub Desktop does.** Rejected. Megabytes per
  platform, one more thing to keep patched, and it ignores the git the user
  already chose and configured.

### Shared code between macOS and Linux

- **A. No shared code; shared behaviour and shared test data.** Chosen. Each
  app has its own core (`UpstreamKit` in Swift, `linux/core` in Rust). They
  share `docs/REQUIREMENTS.md` and `fixtures/git/`: real git output that
  both parsers are tested against, generated by one script. The git layer is
  small — git is the shared engine — so two copies of the parsing cost less
  than the bridge in B.
- **B. A Rust core used from Swift through a C ABI (or UniFFI).** Rejected
  for now. One implementation of parsing and forge clients, but a Rust
  toolchain in the Mac build, generated bindings, and async and error
  bridging between Swift concurrency and Rust. **Revisit** when the forge
  clients (three forges, two platforms) grow large enough that keeping two
  copies in step costs more than the bridge.
- **C. Swift on Linux too.** Rejected. Swift runs on Linux, but its GTK
  bindings are thin and little-used; we would be maintaining them.

## Decision

Native toolkits, the system's git, and no shared code beyond the
requirements and the fixtures.

### Running git

All in `Git.swift` (and its Rust counterpart):

- **Which git.** A path set in Settings, then `/opt/homebrew/bin/git`, then
  `/usr/local/bin/git`, then `/usr/bin/git`. The last is a shim until the
  Command Line Tools are installed: run without them it opens Apple's
  install dialog instead of answering, so it counts only once
  `xcode-select -p` succeeds. With no git, the window says how to install
  it. On Linux, `git` on the `PATH`.
- **Every call** gets `-c color.ui=false -c core.quotepath=false --no-pager`,
  `GIT_TERMINAL_PROMPT=0` (a prompt nobody can see would hang the call) and
  `GIT_OPTIONAL_LOCKS=0` (a background `status` must not take the index lock
  and make the user's own `git commit` in a terminal fail).
- **Output** is read from stdout and stderr at once: reading one to the end
  while the other's pipe fills would deadlock (a test pins this). Cancelling
  the task terminates the process, so a stale refresh never finishes late.
- **Machine formats only**, never the human output, which changes with
  version and locale.
- **git 2.38 or later**, for `git merge-tree --write-tree`, which previews a
  merge's conflicts without touching the working tree. Ubuntu 22.04 ships
  2.34; its users need a newer git, and the app says so.

### Refreshing

The skeleton refreshes when the app becomes active and on ⌘R. Next, a file
watcher (FSEvents on macOS, `GFileMonitor` on Linux) on the working tree and
`.git`, debounced, ignoring `.git/index.lock` churn, with at most one status
run per repository in flight and later requests coalesced into one.

### Large output

Lazy rows for the changes list and diffs. History is read in pages
(`git log -z --format=… --max-count=… --skip=…`). A diff too large to render
usefully (thousands of lines changed) asks before it is drawn, as GitHub
Desktop does.

### macOS 26 and Apple silicon only

`platforms: [.macOS("26.0")]` in `Package.swift`, `LSMinimumSystemVersion`
26.0 and `LSArchitecturePriority` arm64 in `Info.plist`, and
`swift build --arch arm64` in `scripts/build-mac.sh`. No `#available`
branches, no Intel slice, the current SwiftUI and Observation throughout,
Swift 6 strict concurrency. The skeleton's bundle is 380 KB and uses 51 MB
with a 4,000-file status on screen.

### Layout

```
upstream/
  AGENTS.md (CLAUDE.md → it)  README.md  LICENSE  Makefile
  docs/        REQUIREMENTS.md, plans/, INSPIRATIONS.md, memory/
  fixtures/git/  real git output; scripts/make-fixtures.sh writes it
  scripts/     build-mac.sh, make-fixtures.sh (build-linux.sh later)
  macos/       Swift package
    Package.swift  Info.plist  make-icon.swift
    Sources/UpstreamKit/   git, parsers, models, forge clients — no UI
    Sources/Upstream/      SwiftUI app
    Tests/UpstreamKitTests/
  linux/       Cargo workspace, when it starts
    core/      git, parsers, models, forge clients — no UI
    app/       GTK4 + libadwaita
    data/      .desktop, metainfo, icon (io.github.vivekg7.upstream)
```

The same split as Dhun: a UI-free core that the tests cover, and a thin app
over it. The Linux folder and its `make` targets arrive with its code, not
before.

## Plan

1. ✅ Skeleton: add a repository, its changes and branch, a file's diff;
   fixtures and tests; the arm64 bundle.
2. The checkbox commit: stage exactly the checked files and lines
   (`git apply --cached` for partial files), commit, amend. The part most
   likely to go wrong is partial staging of renamed and new files; it gets
   fixture scenarios of its own.
3. The file watcher.
4. Branches, remotes (fetch, pull, push, publish) and HTTPS credentials
   ([002](002_forges_github_first.md)).
5. History, then conflicts, then discard to Trash, stash, settings.
6. GitHub sign-in, PRs and CI ([002](002_forges_github_first.md)).
7. Linux, in a plan of its own once the Mac app covers the Changes, History
   and Branches requirements.

## Open questions

- **Signing for public release.** Ad hoc signing is fine for the owner, but
  anyone else meets Gatekeeper's warning and has to allow the app by hand. A
  Developer ID and notarisation need a paid Apple Developer account. Decide
  before the first public release; a Homebrew cask is the other half of
  easy installation.
- **Linux packaging.** A Flatpak sandbox has no host git, hooks, SSH agent
  or credential helpers; reaching them means `flatpak-spawn --host`, which
  needs the `org.freedesktop.Flatpak` permission and so is effectively
  unsandboxed. A native package (`.deb`, `.rpm`, a tarball, or `cargo
install`) avoids the problem. Decide in the Linux plan.
